# Snapbar

![Snapbar icon](assets/branding/snapbar-48.png)

Microsoft Teamsが公開する**内容領域だけ**（画面共有していない待機中も同じ領域）、または自分が共有中の**確定済みモニターだけ**を、1クリックまたは会議中の`Ctrl + Alt + S`でWindowsクリップボードへコピーする軽量Windowsアプリです。

![Snapbarの操作デモ](assets/demo/snapbar-demo.gif)

## ダウンロード

Windows向けのインストーラーとポータブル版は、[GitHub Releases](https://github.com/Ray-d3v/Snapbar/releases)で配布します。

- `Snapbar-Setup-x64.exe`: ユーザー単位インストーラー
- `Snapbar-portable-x64.exe`: インストール不要の実行ファイル
- `Snapbar-SHA256SUMS.txt`: 正式リリースの配布ファイルのSHA-256チェックサム

正式リリースは `vMAJOR.MINOR.PATCH` タグからGitHub Actionsで検証・ビルドし、インストーラーとポータブル版を公開します。

インストーラー版は「Windowsサインイン時にSnapbarを自動起動」が既定で有効です。インストール時の追加タスク画面で解除できます。

現在はコード署名していないため、Windows SmartScreenの警告が表示される場合があります。

## 動作方針

- インストーラー版はWindowsへサインインすると自動起動し、通知領域に常駐してTeams会議をローカル監視します。ポータブル版は手動で起動します。
- 自動起動はユーザー単位で登録し、アンインストール時に削除します。上書きインストール時に追加タスクを解除した場合も登録を削除します。
- 会議へ参加していない間はタイトルバーの操作UIを表示しません。
- 会議参加を複合条件で確認すると、対象Teamsウィンドウのタイトルバー中央へ小さなSnapbarピルを自動表示します。
- 会議参加中だけ`Ctrl + Alt + S`をWindowsのグローバルショートカットとして登録します。別のアプリにフォーカスがあっても、共有コンテンツを同じ安全なキャプチャ処理で撮影できます。会議退出後は登録を解除します。
- Teamsを最小化した場合は退出扱いにせず、Snapbarだけを非表示にします。Teamsを復元すると再表示します。
- 他の参加者から受信している共有コンテンツは、対象Teamsウィンドウが最小化されている間は`Ctrl + Alt + S`でも撮影せずクリップボードを変更しませんが、会議状態は維持され、Teamsを復元すると撮影できます。
- 会議退出を一定時間確認するとSnapbarとキャプチャセッションを停止し、通知領域で次の会議を待ちます。
- 通知領域のSnapbarアイコンを右クリックして`Snapbarを終了`を選ぶと、会議中かどうかに関係なく直接終了します。
- 展開したタイトルバー操作列の電源ボタンでは、アイランド全体を使って「Snapbarを終了しますか？」と`終了`／`キャンセル`を表示します。`終了`を押した場合だけ終了し、`キャンセル`で通常の操作列へ戻ります。ホバー解除・非表示・対象切替でも確認を取り消します。
- 終了操作では操作UIを直ちに隠し、キャプチャや監視スレッドの停止完了をUIスレッドで待たずに終了します。
- キャプチャの開始・再開始もバックグラウンドで行います。開始中に共有対象が変わった場合は古い結果を破棄し、開始処理を重複させず最新の対象へ切り替えます。開始失敗・セッション終了・フレーム取得不能が続く場合は、共有の証拠がある間だけ約5秒の間隔で再試行します。
- 一時的なフレーム取得失敗による状態ドットのオレンジ表示には750msの猶予を設けます。これは表示だけの猶予で、共有終了や対象変更は直ちに撮影権限を失効させます。共有の証拠が残っている場合は取得待ちでも撮影要求を受け付け、最新フレームとUIAの再確認を行います。
- キャプチャの準備完了後は、次の定期確認を待たず描画時に緑へ反映します。撮影前のUIA確認中は新しいバックアップ走査を延期し、撮影要求の時刻とフレーム到着順序を同じ同期境界で確定して、要求直後の有効なフレームを取りこぼさないようにしています。
- Teamsが「共有コンテンツ ビュー」の領域を公開していれば、画面共有していない待機中でも同じ領域を撮影できます。招待表示があることだけを理由に撮影を禁止しません。
- アップロード、テレメトリ、クラウド認証、Windowsサービスはありません。

タイトルバーの表示パターンは起動引数で選べます。引数なしでは、ホバー時に操作列がタイトルバーの下側へ少し広がります。`--inline-titlebar`（短縮形`--inline`）を付けると、ホバー時に操作列がタイトルバー内だけで横方向へ展開します。タイトルバーの色取得は表示更新とは別のスレッドで行い、連続してホバーを出入りしても色取得の完了を待たずに展開・縮小します。別のウィンドウに覆われた点や、取得中にTeamsの位置・サイズが変わった結果は使いません。
色取得は背景色用の点と下端の境界色用の点を含むタイトルバーの細い帯だけを一度読み取り、寸法が変わらない間は32bppバッファとメモリDCを再利用します。複数点で境界色を確認し、背景色と境界色を組にして表示へ使います。色取得のために画面全体をコピーしたり、画像ファイルを保存したりする処理はありません。

GitHub Releasesのインストーラー版は、Windowsサインイン時の自動起動、インストール完了時の起動、スタートメニュー、任意で作成するデスクトップショートカットのすべてを引数なしで起動します。そのため、通常のインストール操作では、ホバーすると操作列がタイトルバー下へ約20px広がる表示が既定になります。タイトルバー内だけで完結する表示へ切り替えたい場合は、インストール先の`Snapbar.exe`へ`--inline-titlebar`を付けて起動します。

通常起動ではアイランドと撮影フラッシュを画面共有・録画から除外します。紹介するときは、展開した終了ボタンに5秒以上ホバーして「デモモード」を開き、ONへ切り替えてください。OFFで共有から再び除外します。終了ボタンの通常クリックは従来どおり終了確認を開きます。デモモードは保存せず、次回起動はOFFです（`--demo-mode`または既存の`--recordable-overlay`で明示起動した場合はON、`--exclude-overlay-from-capture`を併用するとOFF）。

デモは画面全体の共有を想定しています。Teamsウィンドウだけの共有では、別ウィンドウであるアイランドが含まれるかは共有方式に依存します。撮影中はトグルに「撮影中」と表示し、切替操作を受け付けません。

## 会議の自動検出

外部EXE向けのTeams参加・退出イベントには依存せず、この端末上のTeams UIを監視します。

1. `SetWinEventHook`でウィンドウの生成、表示、前面への切り替え、最小化、移動、サイズ変更を受信します。文字入力のカーソルやUI内部の細かな変化では、会議検出を繰り返しません。
2. イベント取りこぼし対策として約700ms間隔のウォッチドッグ確認も行います。
3. Teams候補ごとに以下のローカル信号を確認します。
   - Teamsプロセス／Teams会議ウィンドウ
   - `TeamsWebView`子ウィンドウ
   - `TeamsVideo`子ウィンドウ
   - Windows UI Automation上の`退出`、`通話を終了`、`Leave call`などの操作
   - UI Automation上の通話時間／退出コントロールを示す安定した`AutomationId`
   - UI Automation上の共有コンテンツ要素
4. 単発の検出だけでは会議参加と判定しません。退出／通話時間など複数の強い信号が同じウィンドウで2回以上、約250ms安定した場合に参加確定とします。証拠が弱い場合は従来どおり約1.1秒確認します。候補が見つかった後は安定確認の期限に再走査し、次の700ms周期を待ちません。
5. 退出は、会議信号の消失を2回以上かつ約1.4秒継続して確認してから確定します。
6. 最小化中は会議状態を維持します。

`TeamsVideo`やTeamsのUIA構造は公開契約ではないため、特定の1要素だけに依存せず、WinEvent、子ウィンドウ、UIA、継続時間を組み合わせています。
UIAクライアントは専用スレッドで再利用しますが、会議と共有の証拠は各スキャンで新しく検査します。判定対象になる表示中のUI要素だけから、名前・識別子・種類・表示状態をまとめて取得し、個別の問い合わせを減らしています。応答済みのカレンダーやチャットを同じスキャンで二度調べず、UI情報がまだ空の場合には再試行します。プロセス名のキャッシュもPIDと生成時刻で識別した不変の名前だけを対象にし、取得失敗は再試行します。

会議状態が変わったら表示へ直接通知し、通常の250ms同期周期を待たずに反映します。連続するウィンドウイベントは1件の再走査要求へまとめ、走査完了から最低100ms空けてUIAの連続実行を抑えます。表示通知も最大1件で、監視スレッドやUIA要素の永続キャッシュは追加しません。実際の表示時間にはTeams側のUI準備とUIA取得時間も含まれます。

## 共有コンテンツ領域の確定

通常の撮影では、確定した共有コンテンツ要素の現在の名前・種類・表示状態・矩形だけを一括確認し、UIAツリーの全探索や35msの安定待ちを繰り返しません。要素の探索は初回、構造・表示状態・範囲・ウィンドウ配置の変更時、および変更通知の取りこぼしを検出する低頻度のバックグラウンド確認で行います。UIAクライアントと要素は専用MTAスレッドが所有します。変更通知を登録できない環境では、安全のため従来の全探索へ戻ります。
静止中も、保持画像が最新受信フレームで、現在のUIA矩形・変更世代・画像サイズと一致し、確認中に新しいフレームが届かなければ、その画像を直接コピーします。この条件を満たさない場合は新しいフレームを取得し、必要ならUIA要素を維持したままキャプチャセッションを再作成します。
共有範囲の現在値・変更世代・画像サイズ・ウィンドウ位置を確認します。新規フレーム取得の経路では要求後の描画時刻も確認します。Teamsの応答やGPU、クリップボード、任意のPNG保存先による待機は残り、撮影全体の所要時間を保証するものではありません。一時的な取得失敗後もボタン・ショートカットから再試行できます。

共有画面の切り抜きは画像内容やテーマ色から推測しません。TeamsがWindows UI Automationへ公開する共有コンテンツ要素を正本にします。

1. 初回と再検出が必要な場合に、選択中のTeams HWNDからWindows UI Automationルートを取得します。
2. UIAサブツリー全体を走査し、`IsOffscreen == false`で、Accessible Nameに「共有」と「コンテンツ」の両方を含む要素を探します。英語環境では`shared content`、`presented content`などを使用します。
3. 実機で確認された`ControlType.MenuItem`を最優先し、`Document`、`Pane`、`Custom`、`Group`、`Image`も互換候補として扱います。
4. `AutomationId`や動的な`fui-*`クラス名には依存しません。
5. `BoundingRectangle`がTeamsウィンドウ内にほぼ完全に収まり、十分な大きさであることを確認します。
6. WebView2のUIAツリーが未展開の場合は、`ElementFromPoint`で一度ウォームアップし、短時間待って再走査します。
7. 初回や矩形変更時には同じ矩形を2回取得し、各辺が数ピクセル以内で安定した場合だけ確定します。画面上の位置・サイズとキャプチャ寸法が前回と同じで、今回新しく読んだUIA矩形も前回の確定矩形と完全一致する場合は、重複する35msの安定待ちを省きます。
8. UIA画面座標を、その時点のWindows Graphics Capture画像座標へ変換します。DPI、負座標を含むマルチモニター、ウィンドウサイズの違いを吸収します。
9. 確定したUIA矩形には、色解析、三層境界、行・列投影などの画像補正を適用しません。
10. 撮影要求前、フレームの切り抜き時、出力前のUIA矩形とウィンドウの位置・サイズが一致することを確認します。最新受信画像を直接使う短縮経路以外では、フレームの描画時刻も照合し、要求前のUIA確認より古い画像は使いません。

共有領域を一意に確定できない場合は、Teamsウィンドウ全体や画像推定範囲をコピーせず、失敗として停止します。

共有領域のUIA走査では、共有要素になり得る種類のうち、表示中で名前を持つ候補の名前・種類・表示状態・矩形を一括取得し、全要素への個別問い合わせを減らしています。撮影時の座標確認はデスクトップ全体を再列挙せず、対象TeamsのDWM表示枠を一度に取得します。UIAのCOM初期化と解放も同じスレッド内で対応させています。現在のUIA矩形を再確認したうえで、保持画像が最新受信フレームであり、確認中にも新しいフレームが届かなかった場合は、その画像を直接コピーします。この経路では静止画面のための再起動や新規フレーム待ちはありません。UIAやクリップボードの処理時間は残ります。

開いているTeamsのUIA走査時間だけを調べる場合は、`cargo test live_teams_uia_scan_timings -- --ignored --nocapture`を実行できます。従来の個別取得と一括取得の時間、共有矩形の有無・一致を表示し、画像取得・クリップボード変更は行いません。

通常起動時から診断ログを `%LOCALAPPDATA%\Snapbar\Logs` に自動保存します。通知領域（右下の常駐アイコン）でSnapbarを右クリックし、「ログを開く」を選ぶとその時点のログを `%TEMP%\SnapbarLogViewer` に閲覧用コピーとして作成し、メモ帳で開きます（閲覧用コピーは最大8ファイル）。元のログには引き続き記録します。読み取り中に発生した問題を確認する場合は、再度「ログを開く」を選んでください。特別な起動引数は不要です。

ログにはUTCのUnix時刻（ミリ秒）、起動からの経過時間、ビルド識別情報、撮影要求番号、入力方式、準備状態の変化と失敗理由、UIA確認時間、フレーム・取得矩形、DPI・配置・ホバー変化、クリップボード・PNG処理時間を記録します。同じ `request` 番号の行を追うと、UI入力から撮影完了までを分析できます。フレーム受信など別スレッドのイベントは `request=0` となるため、時刻で照合します。画像・会議名・会議本文・クリップボード内容は記録せず、外部送信もしません。エラー文には保存先のパスが含まれる場合があります。

書き込みは専用スレッドで実行し、混雑時は撮影を待たせずログを省略して `log_queue_dropped` に件数を記録します。1ファイル約4MiBで切り替え、現在のログと直前のログを保持します。起動時には古いログを整理し、通常の単一起動では過去分を含め最大8ファイル（約32MiB）に抑えます。問題発生後は再起動前に「ログを開く」から保存・共有してください。これは障害解析用のローカル診断ログで、改ざん防止を備えた監査証跡ではありません。

### 自分のモニター共有

自分が共有しているモニターは、共有バーの位置から推測しません。Teamsの発表者ツールバーはドラッグできるため、位置は共有対象の根拠にならないからです。

1. 発表者ツールバーのUI Automationから、`share-button`の「共有を停止」操作、または「画面を共有しています」に相当する表示を確認します。
2. Teamsの`ms-teams.exe`が作成したトップレベル`ScreenBorderWindow`だけを候補にします。可視、最前面、非cloaked、`WDA_EXCLUDEFROMCAPTURE`であることも確認します。
3. 確認済み共有枠が1個だけ存在し、その現在の矩形が列挙したモニター1台の矩形と完全一致した場合だけ、その`HMONITOR`をWindows Graphics Captureへ渡します。解像度や座標の固定表は使いません。
4. キャプチャ開始時、フレーム更新時、出力直前に共有枠とモニターを再確認します。共有終了や対象変更で撮影タスクの出力権限が失効した場合も、書き込み開始と同期して停止します。
5. 自分のウィンドウ共有では共有枠がモニター境界と一致しないため、現時点では誤撮影防止を優先して撮影ボタンを有効化しません。

## タイトルバー操作UI

Snapbarは会議コンテンツの上へ常時重ねず、Teamsの**タイトルバー中央の空き領域**だけを使用します。

### 通常時

- 30pxのタイトルバー帯の上端1 logical pxをWindowsの外周線用に残し、その下の約`92 × 29px`を、最小化・最大化ボタンと同じ考え方の`46px`幅セル2個として収めます。
- 全体背景、ラベル、下方向のせり出しは表示せず、状態ドットと`16px`のニュートラルなカメラアイコンだけをタイトルバー上へ置きます。撮影可能かどうかは状態ドットで判別し、赤い丸ボタンはホバー展開後だけに表示します。周囲のタイトルバーは透明なままです。
- ホバー入力範囲はこの`92 × 29px`の矩形と一致します。上端の外周線と左右の領域はTeamsへ透過するため、枠線の描画やウィンドウのドラッグを妨げません。

### ホバー時

状態ドットとカメラアイコンは、開閉の途中も消さずに表示します。状態ドットは説明の切り替え中も残り、待機位置と説明欄の間を滑らかな直線軌道で移動します。ホバー解除時も縦横が同時に進み、タイトルバーの定位置へ斜めに収束します。閉じるときはカメラの円形背景だけを縮め、アイコンは同じ大きさのまま待機位置へ戻します。

約16ms（60Hz表示の約1フレーム）ホバーすると、タイトルバーの下端から一体につながって膨らむ動きで操作列を展開します。タイトルバーに重なる部分は展開中も透明に保ち、下方向20pxまで膨らむ部分だけをTeamsのタイトルバーから採った背景色と境界色で描きます。下端の区切り線はアイランドの肩から底へつながり、開閉と一緒に変形します。黒への色変化は加えず、文字とアイコンも背景の明るさに合わせます。カメラは1つのアイコンのまま下端と一緒に移動し、円形の撮影背景が現れます。補助コントロールも面に沿って広がり、閉じるときは少しゆっくり逆の動きでタイトルバーへ戻ります。

大きさは固定`288 × 50px`の範囲内に収め、上端1 logical pxをWindowsの外周線用に残します。可視面は最大`288 × 49px`（タイトルバー内29px＋下方向20px）、肩は深さ8px・内側24px、下角は約`R12px`です。

補助アイコンは説明文とは別に現れ、開くときも閉じるときも同じ下端の動きをたどります。縮小時はタイトルバーへ近づきながら少し内側へ寄り、カメラ位置へ近づくまでゆっくりフェードします。

待機時のカメラアイコンと展開後の撮影ボタンは、中心のX座標を揃えています。ホバー後もカーソルを横へ追い直す必要はありません。

保存ボタンに1秒続けてホバーすると、同じアイランド全体が保存説明へ切り替わります。この待機は実際の保存ボタン上のホバーだけを対象とし、ボタンを離れると直ちに取り消します。通常の`288 × 50px`範囲（可視`288 × 49px`、HWND`304 × 52px`）を保ち、inlineの29px、presenterの展開時49pxも変えません。中央寄せの幅204 logical pxの2段表示に収め、上段には左側の小さな戻る矢印、PNG保存ラベル、直接操作できるON/OFFスイッチを置きます。下段にはWindowsから毎回取得した実際のScreenshotsフォルダーのフルパスを表示し、収まる場合は中央寄せ、長い場合は折り返さず同じ行を横スクロールできます。`戻る`またはホバー解除で通常表示へ戻ります。説明表示中のスイッチ操作は同じページを開いたまま設定を切り替え、進行中の保存先パス取得を継続します。通常の操作列で保存ボタンをクリックした場合は、クリック後に1秒の待機を数え直します。説明表示中にフォルダー作成・コピーは行いません。

展開後の左側には、配置の動かない2段コンテキスト表示があります。通常時は状態ドットと会議状態を示し、最初にボタンへカーソルを重ねたときはその説明をすぐに表示します。別のボタンへ移る場合は160ms連続してホバーした後に、上段を`撮影`、`PNG保存`、`再検出`、`終了`の機能名へ切り替えます。ボタンを離れた時点（ボタン間の隙間へ移った場合を含む）で次の説明への待機は直ちに取り消しますが、表示中の説明はアイランドの折りたたみまたはページリセットまで維持します。隙間はクリック領域を持ちません。下段には機能の補足を分離して表示し、撮影ではキーキャップ風の`Ctrl+Alt+S`、PNG保存では`ON/OFF`を示します。常設の`コピー済`テキストは表示せず、撮影成功時だけ撮影ボタンを約2秒間同じ位置の緑のチェックへ切り替え、その後カメラへ戻します。チェック表示中も連続撮影できます。撮影失敗時は警告アイコンと`要確認`を説明より優先して表示し、保存失敗などのエラーも成功チェックで隠しません。説明欄の外側角丸背景は表示せず、ショートカットのキーキャップだけを残します。操作列の左右には従来より8 logical pxずつ余白を追加しています。この短い補足表示と保存説明は同じ高さ境界内で表示し、保存説明への切り替えは短いフェードだけです。Teamsとの前後関係と撮影ボタンの位置は維持します。

Snapbarはデスクトップ全体の常時最前面にはせず、対象のTeams会議ウィンドウの直上だけに配置します。別のアプリのウィンドウがTeamsへ重なった部分ではSnapbarもその背後へ入り、Teamsを再び前面へ出すとタイトルバーと一緒に前へ戻ります。

展開後の各操作は`30 × 30 logical px`のクリック領域を維持しながら、見た目のボタン面を`28 × 28 logical px`へ一段内側に収めています。保存・再検出・終了は通常時に背景を持たず、ホバー時だけ`28px`の円形背景を表示します。保存ONは緑のフォルダーアイコンと小さな状態ドットで示します。これにより隣接ボタン間には見た目上約8pxの間隔ができ、既定表示では操作列をアイランドの可視領域の上下中央に揃えます。

左から次の操作を配置しています。

- 状態表示／ホバー中の機能説明
- Windowsのスクリーンショットフォルダーにも保存するトグル
- 共有画面を撮影してクリップボードへコピー
- 会議・共有の再検出
- Snapbarを終了

カーソルが操作列から外れて約50ms経過すると自動で縮みます。ホバー判定はGPUI要素ではなく、オーバーレイHWNDへ`SetWindowSubclass`で追加した単一のWin32状態機械が`TrackMouseEvent`／`WM_MOUSELEAVE`とウィンドウタイマーを処理します。タイマー発火時には`WindowFromPoint`でも実際のポインター位置を再確認し、展開中だけ低頻度の安全確認を行います。クリック固定と常時カーソルポーリングはありません。

### 自分が画面共有中

Teamsの共有コントロールバーを独立したウィンドウとして検出すると、Snapbarは会議タイトルバーから離れ、共有バーの下辺中央へ隙間なく接続します。このときはタイトルバー用の帯形状を再利用せず、四隅を約`R16px`まで丸めたピル寄りの角丸四角へ切り替えます。待機時から約`92 × 39px`の操作面を不透明で表示し、操作面内には状態ドットとニュートラルなカメラアイコンを表示します。Teamsの共有枠がモニター1台と一意に一致すると撮影可能になり、赤い撮影ボタンはホバー展開後だけに現れます。ホバー中は同じ角丸とネイティブ入力領域を保ったまま、中央基準で最大`288 × 49px`へ広がります。共有バーが展開・縮小・移動している間は、その実ウィンドウ矩形を約8ms周期で追い、Snapbarも同じ下辺へ追従します。共有バーが一時的に隠れた場合はSnapbarも隠し、共有終了後は通常の会議タイトルバー形状へ戻ります。共有バーのタイトル文字列は操作中に変わるため、初回検出後は同じHWNDと、横長形状・最前面帯・キャプチャ除外属性を組み合わせて追跡します。

### インライン時（`--inline-titlebar`）

- 会議UIが表示されると、92pxの待機セルが表示されます。そこへホバーすると、操作列が横方向へ展開します。
- 30pxのタイトルバー帯の上端1 logical pxをWindowsの外周線用に残し、表示面は最大`288 × 29 logical px`に収めます。下端をタイトルバー下端へ固定するため、展開しても外周線を隠さず、タイトルバー下側へもせり出しません。表示面はタイトルバーの色に合わせ、明度に応じて文字やアイコンの色を切り替えます。
- 展開は中央のカメラ位置を軸に、背景が左右へ約180msかけて滑らかに広がります。30fpsの画面録画でも途中の5〜6フレームを追えるテンポで、操作ボタンも中央から左右へ連続的に散開し、最後にごく小さくバネで収まります。閉じている途中で再ホバーした場合も、現在の幅から開き直すため、中央のボタンだけで一度止まる二段階表示にはなりません。形状は変えず、ホバー判定のデバウンスも維持します。
- 状態、保存先、撮影、再検出、終了を1列に保ち、ポインターが実際の表示面から外れると既存のデバウンス後に92pxへ戻ります。会議終了・Teams最小化・安全領域の変化でも非表示になります。
- タイトルバーの安全幅が足りない場合は、同じ上端インセットを保った`46 × 29 logical px`のカメラセルへ縮退します。
- 既定のホバー展開パターンへ戻すには、起動引数なしで`Snapbar.exe`を起動します。

### 配置と狭いウィンドウ

- `DWMWA_EXTENDED_FRAME_BOUNDS`でTeamsの表示枠を取得します。
- タイトルバー内の表示帯は30 logical pxで算出し、妥当なキャプションボタン下端へ揃えます。最大化時に変動するボタン領域の上端や縦幅には依存せず、下端が短すぎる場合はDWM表示枠上端からの既定位置へ補正します。
- `DWMWA_CAPTION_BUTTON_BOUNDS`は横方向の境界だけに使い、右側の最小化・最大化・閉じるボタン領域を避けます。
- 左側の会議名と右側のキャプションボタンを避けた中央領域へ配置します。
- `288 × 50px`は論理寸法です。モニターをまたいだときはWindowsのモニター別DPI倍率へ追従し、描画面、入力領域、角丸、操作ボタンを同じ比率で物理ピクセルへ拡大します。モニターの生の解像度や物理サイズには比例させません。
- Teamsの移動、最大化、スナップ、別モニターへの移動、DPI変更へ追従します。
- 移動やサイズ変更中も、Teamsからの通知を受けた追従処理が同じワーカーで位置を更新し、通知を取りこぼした場合だけ定期確認で補います。
- タイトルバーの移動やサイズ変更はWinEvent通知を受け取ると同じ追従処理へすぐ伝え、通知を取りこぼした場合だけ既存の定期確認で補います。これによりドラッグ中もSnapbarがTeamsの位置に追従します。
- 横幅が足りない場合は、`46 × 29px`の透明なキャプションセル内にあるカメラアイコン1個だけへ縮退します。
- カメラボタンも安全なタイトルバー領域へ収まらない場合は、Teamsの操作を妨げないようSnapbarを非表示にします。
- タスクバーとAlt+Tabには表示せず、Teamsからフォーカスを奪いません。
- Snapbar自身はキャプチャ画像から除外します。

通知領域のSnapbarアイコンを右クリックすると、以下を実行できます。

- **会議を再検出**
- **Snapbarを終了**

## スクリーンショット

- 撮影結果は必ずWindowsクリップボードへコピーします。
- フォルダーアイコンを有効にした場合だけ、Windowsが設定しているScreenshots既知フォルダーへPNGを保存します。
- 保存時は撮影時に確定したRGBA画像をそのままPNGへ書き込みます。Windowsクリップボードを読み直して保存元にすることはありません。
- 保存トグルの初期値はオフです。
- 保存設定は`%LOCALAPPDATA%\Snapbar\settings.conf`へ保持します。
- 撮影成功後、実際に取得した共有領域へ短い白いフラッシュを表示します。他参加者の共有では対象Teamsウィンドウの直上に置くため、Teamsより前にあるアプリに覆われ、完全に隠れていればフラッシュも見えません。デモモードONでは、このフラッシュも画面共有・画面録画へ映ります。
- カメラボタンは左ボタンを押した時点で撮影を開始します。離すまで待たず、離した際の二重撮影も行いません。押した後でポインターを外へ動かしても撮影は取り消しません。
- 撮影中もクリックとショートカットを受け付け、次の撮影を1回だけ保留します。それ以上の連打は同じ保留へまとめ、処理完了後にその時点の共有画面を撮影します。会議や撮影対象の切り替えでは古い保留を取り消します。連打速度が処理能力を超えた場合、押した回数と撮影枚数は一致しません。
- 次の撮影前には前回のフラッシュを消します。フラッシュは1つのワーカーで管理し、重複表示しません。保留撮影が続く間は途中のフラッシュを省略し、最後の撮影成功時に表示します。
- フレーム取得が停滞した場合は、同じ撮影対象のキャプチャセッションを1回だけ作り直して再試行します。他参加者共有では各キャッシュ更新を現在の確定UIA矩形からのみ行い、撮影要求前から出力前まで矩形とウィンドウの位置・サイズが一致することを必須にします。共有領域の再確認に失敗した場合や矩形が変化した場合は、古い矩形・画像を再利用せず、クリップボードを変更しません。
- 自分のモニター共有を撮影するときは、Snapbar自身のスクリーンショットに操作UIが混入しないよう、Snapbar本体だけを一時的にキャプチャ除外へ切り替え、新しいフレームを取得してから元へ戻します。撮影後の白いフラッシュは元へ戻した後に表示するため、共有・録画側には残ります。
- 共有されているWindowsデスクトップのタスクバーは共有コンテンツに含まれます。
- UIA内容領域の外側にある参加者列、チャット、Teams操作UIは含まれません。共有していない待機画面では、内容領域内のアバターや案内表示が撮影されます。

## メモリと処理負荷

- Windows Graphics Captureセッションは、会議中にTeamsの内容領域を確定できるときだけ開始します。領域が失われた場合・会議退出時には停止します。
- UIA座標の算出だけのためにTeamsウィンドウ全体をCPUメモリへコピーしません。
- CPU側へ取得するのは、他参加者共有では確定済みUIA共有領域、自分のモニター共有では確認済みモニター1枚だけです。
- 最新の切り抜き画像は1枚だけ保持し、同じ`Vec<u8>`を再利用します。フレームごとの大規模なヒープ確保を避けます。
- 待機時のバックアップ更新は約750ms間隔です。撮影時は新しいフレームを最大約200ms待ち、届かない場合はセッションを一度作り直して最大約1.2秒待ちます。他参加者共有で既に200ms以上フレームが届いていない場合は、追加の200ms待ちを省いて再作成へ進みます。直近の到着間隔から次の更新まで200ms以上かかると推定される場合も、この待ちを省きます。推定は再取得の開始時刻だけに使い、保持画像をコピーする根拠にはしません。ただし、Teams内の領域撮影では、現在のUIA矩形と一致し、その確認中にも新しいフレームを受信していない最新画像を直接コピーできます。より新しい受信フレームが未反映の場合は、この短縮経路を使いません。実際の連写速度はUIAの応答時間、共有画面の更新頻度、解像度、クリップボードや保存先の応答時間によって変わります。
- 他参加者共有のUIA走査は約750ms間隔のキャッシュ更新時と、撮影要求・出力の確認時に行います。フレームが届くたびにCPUコピーやUIA走査を行うことはありません。フレームが既に到着しUIA確認・切り抜き処理中なら、不要な再起動を避けるため、同じ要求の開始から最大約1.2秒まで処理完了を待ちます。
- タイトルバーUIのTeams追従は位置が変化した場合だけ`SetWindowPos`を実行します。移動通知を受けた場合は定期確認の期限を待たずに配置を更新します。アニメーションのフレーム通知では形状と入力領域だけを更新し、通知がない間も既存周期で位置とZオーダーを確認します。追従対象の移動だけで重い会議検出を繰り返さず、移動終了と既存のウォッチドッグで確認を続けます。
- ホバーアニメーション中はGPUIの非アクティブウィンドウ向け約30fps制限を使わず、DWMのvsyncへ追従します。ネイティブ入力領域は同じ左右幅が続く行を縦長の矩形へまとめ、1回のリージョン生成で正確な曲線を更新します。実際の描画レートは、Snapbarを表示しているモニターの設定リフレッシュレートとWindowsの描画負荷が上限です。

GPUIとWindows Graphics Capture自体の基礎メモリは必要ですが、旧実装にあったフルフレーム二重コピー、20fpsのCPUキャッシュ、共有前のWGC起動を廃止しています。

## 操作

1. 既定のホバー展開を使う場合は`Snapbar.exe`、タイトルバー内だけのインライン表示を使う場合は`Snapbar.exe --inline-titlebar`を起動します。タイトルバーUIは表示されず、通知領域で待機します。
2. Teams会議へ参加します。
3. 会議参加が確定すると、Teamsタイトルバー中央へ小さなSnapbar操作ボタンが表示されます。
   - 参加者が自分だけで、まだ共有画面がない状態でも表示されます。Teamsが内容領域をUIAへ公開していれば、共有開始前も同じ領域を撮影できます。
4. 既定モードでは待機セルへ約16msホバーして操作列を表示します。インラインモードでも、同じ待ち時間のあとタイトルバー内へ操作列が横に展開します。
5. Teamsの内容領域、または自分のモニター共有が一意に確認され、カメラボタンが赤くなったらクリックします。Teamsにフォーカスがないときは、代わりに`Ctrl + Alt + S`を押します。
6. PowerPoint、OneNote、Teamsチャットなどへ`Ctrl + V`で貼り付けます。
7. 会議退出後はタイトルバーUIが自動で消え、Snapbarは通知領域で次の会議を待ちます。

## 制約

- Windows 11専用です。
- Teams Premium等でキャプチャが禁止されている会議では、OS・Teams側の制限を受けます。制限の回避は行いません。
- Teamsのローカルウィンドウ構造とUI Automation構造は公開契約ではありません。Teams更新時に検出規則の追従が必要になる可能性があります。
- 共有コンテンツ要素をUI Automationから確定できない環境では、誤撮影を避けるため撮影ボタンを有効化しません。
- 自分の共有では、Teamsの共有枠が1台のモニター境界と完全一致する場合だけ撮影します。共有ウィンドウ、複数候補、枠を取得できないTeams版では撮影せず、クリップボードを変更しません。
- 音声のみの会議では`TeamsVideo`がない場合があります。そのため、退出操作など他の会議信号を含めて判定します。
- ZoomやGoogle Meetは現時点では対象外です。
- `Ctrl + Alt + S`を別のアプリがすでにグローバル登録している場合、Windowsの競合回避によりショートカットを使用できません。タイトルバーの撮影ボタンは引き続き使用できます。
- 共有領域が縮小・移動した場合や、撮影待機中に共有終了・対象変更が発生した場合は、安全確認を優先して撮影を失敗させます。失効した撮影タスクはクリップボードやPNGを書き込みません。
- Explorer再起動後は、非表示のトップレベル通知ウィンドウが`TaskbarCreated`を受信してトレイアイコンを再登録します。
- クリップボードに保持するのは最新の1枚です。アプリ内履歴はありません。


### 端末間のタイトルバー・DPI互換性

Teamsの実際の最小化・最大化・閉じるボタンから、同じ高さに並ぶ2種類以上のUIA矩形を確認できた場合は、その下端をアイランドの接続位置に使用します。DWMの標準ボタン領域とTeamsのカスタムタイトルバーの高さが異なる場合を補正します。情報が取れない場合は検証済みのDWM配置へ戻り、チャット内の閉じるボタンなどは位置決めに使いません。
ウィンドウ移動・サイズ・DPI変更に応じて再検証し、Snapbarのクライアント寸法も対象のDPIに対応する304×52論理ピクセルへ揃えます。背景はWindows側のクリップに依存せず、入力領域と同じ輪郭を直接描きます。画面の解像度や物理的なインチ数による倍率の決め打ちは行いません。

### Teams内のズーム変更への追従

TeamsのWindows表示倍率とは別に、Teamsアプリ内のズームでタイトルバーの高さが変わる場合があります。複数の会議操作領域（通話インジケーター・会議コントロール・退出コントロール）の上端と下端が同じ行で一致するときは、その上端をタイトルバー境界として使用します。取得できない場合は従来のタイトルバーボタン／DWMの判定へ戻ります。

タイトルバーの高さに合わせて、アイランドの幅・高さ・アイコン・ネイティブ入力領域を同じ比率で拡大・縮小します。待機中のアイコン列はタイトルバー内、ホバー展開中はアイランド全体の上下中央に置き、展開部分は下端からはみ出します。横幅が足りない場合はカメラ単独表示へ切り替えます。WindowsのDPIとは別に適用し、撮影領域の切り抜きには使いません。検出済みの会議操作領域の座標を約50ms間隔の追従処理で再確認します。全体探索は低頻度に保ち、境界が変わらない間の背景色読み取りも350ms間隔に抑えます。実際の反映時間にはTeamsのUI Automation応答時間が加わります。

極端なTeamsズームでも、複数の会議操作領域から確認した境界は標準タイトルバーの高さ制限で捨てず、展開部分をその境界より下へ配置します。縮小時の背景と入力領域は同じ丸め済み境界を使い、Teamsの区切り線が通る透明な1pxの隙間を防ぎます。

Teamsの区切り線がUIAの会議操作領域より1境界線分上に描かれるため、展開時はその行まで背景で覆います。枠線の色も境界直上の行を優先して取得し、ライトモードの白い会議操作領域を枠線の色として拾わないようにします。待機時の透明表示と入力領域は維持します。

デモモードONで自分が共有中のときは、共有コントロールバー側に加え、検出済みのTeams会議タイトルバーにもUIを表示します。両UIの撮影・PNG設定・再検出・終了は共通の処理へ接続し、監視・ホットキー・撮影セッションを二重に起動しません。デモOFFまたは共有終了で追加のタイトルバーUIを隠します。Teams会議ウィンドウを最小化している間は、タイトルバーUIも非表示です。

枠線の太さはTeamsの境界付近で同色が続く物理ピクセル数から取得し、Teamsのズーム倍率では拡大しません。付け根のアーチは横16・縦10論理pxとし、描画とネイティブ入力領域で同じ輪郭を使います。
