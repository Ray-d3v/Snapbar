# GPT-6レビューの検証と初期修正

対象: beta.170 / a5c9e04。Oracle 0.20.0のGPT-6 Pro回答と、内部ブラウザの回答
（https://chatgpt.com/c/6aa21f90-f5e4-83e8-b7e8-9ffc27195356）を照合した。

## 判断

両回答は、実行中の全探索が優先キューを阻害すること、定期監査の廃止が
別候補の曖昧さを見落とすこと、preflight中のフレーム破棄が再起動につながり得ることを指摘した。
request 11の248msはキュー待ちで、検証そのものは8ms。個々のオレンジ表示の原因や
再起動理由までログだけでは確定できない。

Oracleは以前と完全一致する全探索結果なら2回目を省く案を推奨したが、内部ブラウザは
イベント未通知の過渡状態を確認する機会が減ると指摘した。今回は2回確認を維持する。
UIAが全イベントを通知する保証はない:
https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-eventsforclients

## 実装

- 変更のない定期監査を2段階に分割。初回走査が以前の候補・要素・世代と完全一致した
  場合のみ途中状態を保持し、35ms後の再開までワーカーを要求処理へ返す。
- 再開時にも要求キューを優先。候補不一致・欠落・曖昧さ・世代変更は旧証拠を失効。
  途中状態の破棄と検証成功を混同せず、監査完了時だけ監査時刻を更新する。
- 高速撮影の出力UIA確認は画素mutexを取得する前に行い、取得後にsequence・サイズ・
  layoutを再チェック。既存の単一cropバッファを維持。
- 各監査走査時間、キャッシュ欠落、セッション終了、sequence・layout・サイズ不一致を記録。

## 検証範囲と残件

回帰テストは監査待機と再開時の撮影優先、出力検証失敗時の書き込み禁止、
出力検証中の新フレームによる拒否とmutex非保持を確認する。
実Teamsプロバイダーの遅延改善量は別端末ログによる再測定が必要。

今回、preflight中のフレーム受け入れ条件は広げていない。これには描画前後の時刻付き
UIA証拠、要求ID、失効世代の対応付けが必要であり、番号一致の緩和や要求登録の
単純な前倒しは採用しない。購読ルート交換の再登録、書き込み再試行時のUIA世代検証、
変更起因探索や単一COM呼び出しの長時間占有は残る。完全解消とは扱わない。
